Benchmark report · November 2026

Can a cheap model make senior-level design calls?

I built consult, a skill that makes Claude Haiku write a pre-mortem before it codes and call a board of stronger models for risky changes. Then I measured it on two real codebases with a blind judge. On the changes that ripple through a codebase it beat Sonnet. On small features it made no difference.

How the skill works

Write the review before writing the code

1

A written pre-mortem, every design task

Before the first edit Haiku fills a fixed template: the real need, every place that writes the data it's about to change, every reader, parent/child inheritance, the decision, and the five most likely reasons a strict reviewer would reject it. It costs almost nothing.

2

A board meeting for cross-cutting changes

A new column, table, status or config value, or more than one entry path, triggers a board. The rule is mechanical, so Haiku doesn't get to decide. Two Sonnet seats (architect and product) read the repo, take positions and rebut each other once, then an Opus chair writes a resolution with a plan, rejected options, risks and open questions. About $1–2 and 2–4 minutes.

3

You approve, then Haiku builds

The resolution goes to you before any code is written, with a default answer for every open question. If Haiku gets stuck twice on the same failure, a one-on-one consult diagnoses it.

What I learned

Cheap models skip anything optional

  • A second repo changed the conclusion. The soft pre-mortem looked like a clear win on the first app (8/10 on two tasks for $0.04). On a FastAPI + React codebase it did nothing. The transcripts showed why: Haiku loaded the skill, explored, then decided "one check here covers every path" and skipped the written steps.
  • Make the important steps mechanical. The fix was a required template and a board trigger based on facts (does the plan add a column?) instead of Haiku's own judgment. The board then fired on exactly the task that added a column, and that became the best result of any setup on the hardest task (8, 7 and 7 against Sonnet's 7 and 6).
  • Sonnet alone isn't automatically better. On the first app it scored the same as Haiku (5.9 over 12 runs each). Most misses were design decisions, not code: which user is this, who may call this route, what else reads this status.
  • Measure the human. Counting only tokens, the board looked like a waste. Counting review time, it was among the cheapest options.
Method and caveats

How it was measured, and its limits

  • Two real apps, kept anonymous here: App A (Next.js + Postgres, 6 tasks) and App B (FastAPI + Postgres + React, 3 tasks). Requests were deliberately vague, like "let customers cancel" or "stop new people registering once it's full".
  • Each run works on a throwaway clone and is checked with the repo's own typecheck, lint and unit tests. A blind Opus judge then scores the diff against a hidden checklist without seeing the setup, the meeting logs or the agent's summary.
  • The judge is a model, not a person. Identical runs vary by about ±1 point, and the "minutes" are its estimates. With 3–12 runs per cell, differences under about one point may be noise.
  • I wrote the checklists, and the first pre-mortem was written after seeing the first app's feedback. That's why the second repo was added, and why that version isn't the one that ships.
  • No human was in the loop. In real use you also review the board's plan before any code is written, which these numbers don't capture.
  • An earlier round on six well-specified coding tasks with hidden tests found no benefit: Haiku already solves clear specs, and the skill correctly stays out of the way.
Try it

Install in one command

Works in Claude Code and Codex. Needs uv (or Python 3.9+) and the claude CLI or an API key. The scripts run in their own isolated environment, so they never touch your project's dependencies.

uvx --from git+https://github.com/21ko/consult-skill consult-install            # user-level, Claude Code + Codex
uvx --from git+https://github.com/21ko/consult-skill consult-install --project .  # one repo only

The run records (scores and costs) are in the repository under bench/design/results/, and summarize.py rebuilds every table on this page. The apps' code and diffs are not published.
